# Политика безопасности

Sign-craze управляет firewall, маршрутизацией и web-UI на роутере домашней
сети (Keenetic поверх Entware) и работает с правами `root`. Уязвимости
утилиты затрагивают весь сегмент LAN, поэтому раскрытие координируется
ответственно: сначала фикс и релиз, потом публикация деталей.

Документ охватывает: какие версии получают патчи, как сообщить уязвимость,
что считать уязвимостью, сроки реакции и процесс подготовки исправлений.

## Поддерживаемые версии

Поддерживаются текущая и предыдущая минорные ветки. Старые ветки
не получают патчей: обновитесь до актуальной версии.

| Версия      | Поддержка                                              |
|-------------|--------------------------------------------------------|
| `1.6.x`     | Активная: фиксы безопасности и баг-фиксы              |
| `1.5.x`     | Только критические фиксы безопасности                  |
| `< 1.5.0`   | Не поддерживается                                      |

Текущую версию узнать: `sign-craze --version`. Релизы и changelog:
[GitHub Releases](https://github.com/kittylabassistant/sign-craze/releases) и
[`CHANGELOG.md`](CHANGELOG.md).

## Как сообщить уязвимость

**Не открывайте публичный issue.** Публикация деталей до фикса даёт
атакующим окно на эксплуатацию активных установок.

Используйте один из приватных каналов:

1. **GitHub Security Advisories (предпочтительно):**
   [report a vulnerability](https://github.com/kittylabassistant/sign-craze/security/advisories/new).
   Канал шифрует сообщение, видим только мейнтейнеру, поддерживает
   совместную работу над фиксом и автоматическую публикацию advisory
   после релиза.
2. **E-Mail:** [kittylabassistant@protonmail.com](mailto:kittylabassistant@protonmail.com)
   с темой `SECURITY: <короткое описание>`. Используйте, если нет
   аккаунта на GitHub. Чувствительные детали передавайте после первого ответа
   мейнтейнера.

PGP-ключ не публикуется: GitHub Security Advisories уже передаёт
сообщение по защищённому каналу.

## Что включить в отчёт

Чем полнее отчёт, тем быстрее фикс. Минимально:

- **Версия sign-craze:** `sign-craze --version`
- **Окружение:** модель Keenetic, версия KeeneticOS, архитектура
  (`mipsle` / `mips` / `arm` / `arm64`), версия Entware
- **Компонент:** firewall / routing / web UI (`:9090` / `:9091` /
  `:9092`) / генератор конфигов [sing-box](https://sing-box.sagernet.org/) / install-скрипт / релизный
  бинарь / прочее
- **Описание:** что не так, какой инвариант нарушается
- **Воспроизведение:** минимальная последовательность команд или
  HTTP-запросов; PoC, если есть
- **Влияние:** что атакующий получает (повышение привилегий, чтение
  ключей, bypass firewall, RCE, DoS)
- **Предлагаемая оценка:** [CVSS v3.1](https://www.first.org/cvss/calculator/3.1)
  vector + score, если можете прикинуть; не обязательно
- **Логи и артефакты:** редактируйте перед отправкой, удалите WAN IP,
  MAC, токены провайдеров, `proxy.json` URL outbound, IP клиентов LAN,
  пароли Wi-Fi

Если уязвимость в зависимости (sing-box, [nfqws2](https://github.com/nfqws/nfqws2-keenetic), geo-данные), укажите
это: возможно, апстрим уже знает.

## Сроки реакции

Проект ведёт один мейнтейнер, поэтому сроки указаны в рабочих днях
и без жёстких SLA-гарантий. Обычная реакция:

| Этап                                | Целевой срок            |
|-------------------------------------|-------------------------|
| Подтверждение получения             | ≤ 3 рабочих дней        |
| Первичная оценка и триаж            | ≤ 7 рабочих дней        |
| Фикс для critical/high              | ≤ 30 дней               |
| Фикс для medium                     | ≤ 90 дней               |
| Фикс для low                        | по возможности          |

Категория ставится по CVSS v3.1: critical ≥ 9.0, high 7.0-8.9, medium
4.0-6.9, low < 4.0. Если в течение 7 дней не пришёл ответ, продублируйте
сообщение во второй канал (E-Mail, если писали через GHSA, или наоборот).

## Что считаем уязвимостью

In-scope для sign-craze (репозиторий
[`kittylabassistant/sign-craze`](https://github.com/kittylabassistant/sign-craze)):

- **Повышение привилегий** на роутере через sign-craze: эскалация от
  непривилегированного процесса к `root`, выход из контекста утилиты.
- **Bypass firewall-правил** sign-craze: трафик, который должен идти
  через прокси, идёт мимо; правила `signcraze_*` обходятся через
  предсказуемый вход.
- **Повреждение чужих firewall-правил** не из префикса `signcraze_*`:
  sign-craze не должен трогать сторонние chain'ы / [ipset](https://ipset.netfilter.org/)'ы (см.
  [`docs/OWNERSHIP.md`](docs/OWNERSHIP.md)).
- **RCE / command injection** через web UI (`:9090` Zashboard,
  `:9091` admin REST API, `:9092` Routing Editor) или CLI: исполнение
  произвольных команд на роутере.
- **Path traversal / arbitrary file read/write** через web UI или
  install-скрипты.
- **CSRF на admin REST API** (`:9091`): сторонний сайт в браузере
  пользователя меняет состояние sign-craze.
- **Доступ к web UI с WAN** при штатной установке: порты `:9090`/`:9091`/
  `:9092` должны быть LAN-only.
- **Template injection** в генераторах конфигов sing-box / [Xray-core](https://xtls.github.io/) / [mihomo](https://wiki.metacubex.one/):
  пользовательский ввод (имя outbound, URL прокси) ломает шаблон или
  даёт исполнение.
- **Утечка секретов в логи и support-bundle:** outbound URL, API-токены
  провайдеров, приватные ключи попадают в `/opt/var/log/sign-craze/`,
  вывод `--diag`, `support-bundle` без редактирования.
- **Supply chain в релизе:** подмена релизного бинаря на GitHub
  Releases, расхождение `sha256sums.txt` и фактического файла,
  компрометация GitHub Actions release pipeline.
- **Загрузка чужих бинарей без верификации:** sign-craze скачивает
  sing-box/nfqws2. Отсутствие проверки или возможность редиректа
  на подменённый артефакт считается уязвимостью.
- **DoS sign-craze**, который не может быть восстановлен без
  перезагрузки роутера или ручного вмешательства, при типовом
  пользовательском трафике.

## Что не уязвимость

Out-of-scope: репортить можно, но это будет закрыто как not-a-bug или
переадресовано:

- Уязвимости в `sing-box`, `xray-core`, `mihomo`, `nfqws2`, ядре Linux,
  KeeneticOS, Entware, BusyBox: сообщайте напрямую соответствующим
  проектам.
- Slow loris / трафиковый DoS на сторонний прокси-core (sing-box и т.д.):
  это поведение апстрима, sign-craze его только конфигурирует.
- Атаки, требующие `root` или физического доступа к роутеру: такой
  атакующий уже владеет устройством.
- Атаки на клиентов LAN, использующих доверенный прокси: модель угроз
  sign-craze считает LAN доверенной. Web UI (`:9090` Zashboard, `:9091` admin REST,
  `:9092` Routing Editor) — LAN-only, без HTTP-аутентификации by design. Единственный
  барьер от WAN — NDM INPUT DROP на эти порты. Web-UI, доступный с WAN (из-за
  неверной конфигурации firewall), входит в scope.
- Self-XSS, требующий ручного ввода вредоносного payload в собственный
  браузер.
- Отсутствие современных HTTP security-заголовков (HSTS, CSP) на LAN-only
  endpoint'ах без существенного impact'а.
- Отчёты, основанные только на выводе сканеров без подтверждённого
  impact'а.
- Установка sign-craze в нестандартных условиях (другой роутер,
  изменённые пути, ручная правка `signcraze_*` chain'ов): см.
  [`docs/COMPATIBILITY_MATRIX.md`](docs/COMPATIBILITY_MATRIX.md).

## Процесс координированного раскрытия

1. **Получение.** Мейнтейнер подтверждает получение через тот же канал.
2. **Триаж.** Воспроизведение, оценка impact'а и категории CVSS.
   Спорные отчёты обсуждаются с автором в приватном канале.
3. **Фикс.** Разработка патча в приватном форке / приватной ветке
   GHSA. Релизных preview-сборок до фикса не публикуется.
4. **Embargo.** По умолчанию **90 дней** с момента подтверждения, но
   обычно меньше: фикс выходит, как только готов и протестирован.
   Срок может быть продлён по согласованию, если нужна координация
   с зависимостями или crucial deployment.
5. **Релиз.** Версия с фиксом публикуется в GitHub Releases с
   `sha256sums.txt`. Номер версии: patch-bump текущей минорной ветки.
6. **Раскрытие.** В тот же день или в течение 7 дней после релиза:
   GitHub Security Advisory переводится в публичный режим, в нём
   указаны затронутые версии, фиксированная версия, исследователь
   (с согласия), CVE (если назначен), вектор и обходные пути.
7. **CVE.** При impact'е medium и выше мейнтейнер запрашивает CVE через
   GitHub (CNA `GitHub_M`).
8. **Запись в `CHANGELOG.md`.** Раздел `Security` с краткой формулировкой
   и ссылкой на advisory.

Если исследователь не хочет публичного упоминания, указываем
«анонимно». Если исследователь публикует детали раньше embargo без
согласования, мейнтейнер вправе ускорить публичное раскрытие.

## Безопасность релизов

- **SHA-256 чек-суммы.** Каждый релиз содержит `sha256sums.txt` со
  значениями для всех архитектур (`arm64`/`arm7`/`mipsle`/`mips`).
  Установочный скрипт `install.sh` проверяет sha256 перед заменой
  бинаря.
- **Reproducible-friendly билды.** Сборка идёт в контейнере
  `golang:1.25` через podman/docker, флаги `-trimpath` и
  `-ldflags="-s -w"` фиксированы в `Makefile` (см. цели `all`, `release`,
  `bundle`).
- **GitHub Actions.** Release pipeline в `.github/workflows/release.yml`
  публикует артефакты прямо из CI; никаких ручных загрузок мейнтейнером
  с локальной машины. Workflow не использует secrets с правами на
  push в protected ветки.
- **Subresource integrity для зависимостей.** `go.sum` пинит модули,
  `Makefile` использует фиксированные образы.
- **Скачивание sing-box / nfqws2.** sign-craze тянет апстрим-бинари
  через `--install-auto` / `--dpi on`. Поддерживается проверка
  фактической sha256 относительно ожидаемой. Если интеграция
  верификации сломана, это уязвимость in-scope.
- **Подпись релизов.** Каждый артефакт релиза подписан **[cosign](https://www.sigstore.dev/) keyless OIDC**
  через GitHub Actions (с v1.4.0): рядом с бинарём лежат `.sig` и `.pem`.
  Проверка: `cosign verify-blob --certificate-identity-regexp ... --certificate-oidc-issuer https://token.actions.githubusercontent.com`,
  см. раздел [«Verifying the release»](README.md#verifying-the-release).
  Дополнительно **[SLSA](https://slsa.dev/) build provenance** через `actions/attest-build-provenance@v4`,
  верификация: `gh attestation verify <file> --repo kittylabassistant/sign-craze`.

## Рекомендации пользователям

Минимизация поверхности атаки на роутере:

- **Обновляйтесь.** Включайте проверку обновлений (`sign-craze --check`)
  и читайте `CHANGELOG.md` перед апгрейдом.
- **Web UI - только LAN.** Не пробрасывайте порты `:9090`/`:9091`/`:9092`
  на WAN через NAT/UPnP. Sign-craze ставит DROP на WAN-интерфейсе для
  этих портов в `signcraze_local`, но дополнительная проверка
  правил Keenetic не повредит.
- **LAN считается доверенной.** Если в LAN недоверенные устройства
  (гостевой Wi-Fi, IoT), изолируйте их в отдельный сегмент Keenetic.
  Web UI sign-craze не требует пароля.
- **Не публикуйте `proxy.json`.** Файл содержит URL outbound с
  секретами. При запросах в issue / E-Mail редактируйте перед
  публикацией.
- **Защитите доступ к роутеру.** SSH-ключи вместо паролей, отключите
  Telnet, обновляйте KeeneticOS.
- **Проверяйте sha256.** При ручной установке или offline-bundle
  сверяйте `sha256sums.txt` с тем, что считает `sha256sum` локально.

## Признание исследователей

Мы благодарим тех, кто сообщает уязвимости ответственно.

- Имя/ник исследователя указывается в GitHub Security Advisory и в
  `CHANGELOG.md` (раздел `Security`) с явного согласия исследователя.
- Bug bounty проект **не выплачивает**: некоммерческий проект
  одиночного мейнтейнера.
- Возможна публичная благодарность в README или релизных заметках.

## Юридическая защита исследователей

Исследователям, действующим в рамках этой политики, мейнтейнер sign-craze
не предъявляет претензий по факту тестирования и сообщения уязвимостей.
В рамках этого:

- Тестирование **только на собственном оборудовании** или с письменного
  разрешения владельца. Не атакуйте чужие установки sign-craze без
  согласия.
- Не получайте, не модифицируйте и не публикуйте чужие данные.
- Соблюдайте embargo до публичного раскрытия.
- Не нарушайте применимое законодательство (РФ, страна проживания,
  страна владельца оборудования).

Sign-craze распространяется по [BSD-3-Clause](LICENSE) **без гарантий**
(см. дисклеймер в LICENSE). Эта политика регулирует только взаимодействие
с мейнтейнером, не отменяя условий лицензии.
